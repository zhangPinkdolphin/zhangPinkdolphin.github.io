📌 第三章：从零到有的创作过程


这一章是核心。我带你看 generic_scraper 是怎么一步步被写出来的。


3.1 第0步：发现问题


🤔 "我需要一个工具，能自动从网页上提取信息。
   比如每天自动看某网站有没有上新商品。
   但那些网站需要登录，普通爬虫做不到。"

这就是需求——任何软件的起点。


3.2 第1步：设计方案（想清楚了再动手）


设计画在脑子里大概是这样的：


用户点击"开始爬取"
    ↓
程序收到指令，知道要去哪个网址、提取什么
    ↓
程序打开Chrome浏览器（借用户已经登录好的那个）
    ↓
在浏览器里执行一段"找东西"的指令（JS代码）
    ↓
把找到的结果返回给用户

**💡 关键决策"为什么不用Scrapy？"**
Scrapy 是 Python 最著名的爬虫框架，但它开的是**新的**浏览器——相当于你每次去一个新的超市都要重新登录会员，太麻烦。
而本项目的方案是：**借用你已经打开的 Chrome**，直接用你的登录态。
这就是"站在巨人肩膀上"。

3.3 第2步：搭骨架 —— 用 FastAPI 搭服务器


先写一个最简单的架子（约20行）：


# main.py 第 30 行
app = FastAPI(title="通用爬虫(TMWebDriver版)")
# 这行定义了一个"Web应用"
# 它是整个程序的入口，像前台接待员

**💡 类比**：FastAPI 就是开了一家**餐馆**（服务器），等着客人（用户浏览器）来点菜。`app = FastAPI(...)` 就是"餐馆开张"。

接着定义"菜单"——用户能点什么菜：


# main.py 第 47-58 行
class ScrapeField(BaseModel):
    name: str        # 字段名，比如"title"
    selector: str    # CSS选择器，比如"h1"（告诉程序去找哪个元素）
    attribute: str = "text"  # 提取什么属性，默认文本

class ScrapeRequest(BaseModel):
    url: str                         # 要爬的网址
    fields: list[ScrapeField]        # 要提取的字段列表
    pagination_selector: str = ""    # "下一页"按钮（翻页用）
    max_pages: int = 1               # 最多翻几页
    wait_selector: str = ""          # 等待某个元素出现

**💡 类比**：这就像餐馆的**点菜单**。客人填好"URL"和"字段"，厨房才知道做什么。

3.4 第4步：连接浏览器 —— 借用户的Chrome


爬虫的核心能力是"控制浏览器"。


# main.py 第 64-72 行
def get_driver() -> TMWebDriver:
    """获取TMWebDriver实例（全局单例）"""
    global _driver
    if _driver is None:
        # 连接Chrome扩展（端口18765）
        _driver = TMWebDriver(host='127.0.0.1', port=18765)
        sessions = _driver.get_all_sessions()
        if not sessions:
            raise RuntimeError("浏览器无可用标签页")
        print(f"[OK] 连接成功，可用标签页: {len(sessions)}")
    return _driver

**💡 逐行解释（小白版）**：
- `def get_driver()` → "定义一个叫 get_driver 的功能"
- `global _driver` → "我要用那个全局的 _driver 变量"
- `if _driver is None` → "如果还没连上"（第一次调用）
- `TMWebDriver(host='...', port=18765)` → "连上Chrome扩展，端口18765"
- `get_all_sessions()` → "问问Chrome：你现在开了几个标签页？"
- `return _driver` → "把连好的对象返回出去，其他地方能用"

3.5 第5步：写核心逻辑 —— 怎么爬数据


核心爬取函数 _do_scrape（约100行）是整个程序的灵魂。我们拆解来看：


# main.py 第 283-386 行（精简注释版）
def _do_scrape(task_id, req):
    """后台执行爬取"""
    
    # 第1步：记住当前网页（用完了要回去）
    orig_url = driver.execute_js("return window.location.href")
    # 比如用户在看淘宝，爬完数据后自动跳回淘宝
    
    # 第2步：开始翻页循环
    for page_idx in range(req.max_pages):
        
        # 第2.1步：导航到目标网页
        if page_idx == 0:  # 第一页
            driver.execute_js("window.location.href = '目标网址'")
        else:  # 翻页
            # 找到"下一页"按钮并点击
            btn = document.querySelector('下一页按钮的选择器')
            btn.click()
            # 相当于用户手动点了"下一页"
        
        # 第2.2步：等一会儿（让网页加载完）
        time.sleep(2.5)  # 等2.5秒
        
        # 第2.3步：执行提取JS
        extract_js = _build_extraction_js(req.fields)
        result = driver.execute_js(extract_js)
        # 这句等同于：在浏览器控制台执行一段代码
        # 比如 document.querySelectorAll('h1')
        
        # 第2.4步：把结果存起来
        all_items.extend(result.get('data', []))
        
        # 第2.5步：休息一下（限速，别把网站搞崩溃）
        time.sleep(random.uniform(1.0, 5.0))
    
    # 第3步：恢复原始网页（用完就还）
    if orig_url:
        driver.execute_js(f"window.location.href = '{orig_url}'")
    
    # 第4步：标记任务完成
    _tasks[task_id]["status"] = "completed"

**💡 这是整个程序最精妙的地方**：
1. **零侵入**：用完后自动跳回原网页，用户甚至不知道被"借"过
2. **共享登录态**：直接用的用户当前 Chrome，不需要重新登录
3. **异步执行**：后台线程运行，用户界面不卡

3.6 第6步：动态生成JS提取代码


这是最"聪明"的一部分——程序自己写代码：


# main.py 第 120-248 行（核心片段）
def _build_extraction_js(fields):
    """
    这个函数不提取数据，而是：
    生成一串JavaScript代码，让浏览器去执行
    """
    # 比如用户想提取 h1 的文本
    # 这个函数会生成：
    #   document.querySelectorAll('h1')[0].textContent.trim()
    # 
    # 比如用户想提取 a 的链接
    # 这个函数会生成：
    #   document.querySelectorAll('a')[0].href
    #
    # 然后用 json.dumps() 把这串JS传给浏览器执行
    
    return js_code  # 返回生成的JS代码字符串

**💡 为什么这么做？**
因为"在浏览器里找东西"这件事，JavaScript 最擅长。Python 做不到直接操作浏览器——所以程序用 Python **生成** JavaScript 代码，再让 JavaScript 在浏览器里执行。

>

就像：
- Python 是**指挥官**（制定方案）
- JavaScript 是**士兵**（实地执行）
- 指挥官不亲自上场，但士兵按指挥官的方案行动

3.7 第7步：API接口 —— 让前端能调用


# main.py 第 403-429 行
@app.post("/api/scrape")
async def start_scrape(req: ScrapeRequest):
    """这是前端的"开始爬取"按钮连接的后台"""
    
    # 1. 验证参数
    if not req.url:
        return {"error": "URL不能为空"}
    
    # 2. 创建任务
    task_id = str(uuid.uuid4())[:8]  # 生成唯一ID
    
    # 3. 在后台线程中运行爬取
    t = threading.Thread(target=_do_scrape, args=(task_id, req))
    t.start()  # 启动线程，立即返回
    
    # 4. 告诉前端"任务已启动，这是你的任务ID"
    return {"task_id": task_id}

**💡 为什么用"后台线程"？**
爬一个网页可能需要5-10秒。如果让用户一直等，体验很差。
所以程序说："你先去忙别的，我爬完了通知你。"
这就是**异步**——软件中非常重要的设计思想。

📌 第五章：软件工程的全景图


5.1 generic_scraper 的开发时间线


步骤做了什么用时关键决策
① 需求分析确定「要一个能爬认证站点的爬虫」~5分钟明确"能用已登录Chrome"是核心需求
② 方案调研试了Scrapy、Playwright、CDP直连~2小时全部放弃，**转向TMWebDriver桥接方案**
③ 原型编码写 `_build_extraction_js` + `_do_scrape`~30分钟核心约100行，边写边测
④ 前端对接把已有的 `frontend.html` 接入新API~10分钟复用已有UI，只改API调用
⑤ 测试验证试 httpbin.org + GitHub 搜索~15分钟确认提取正确、翻页正常
⑥ 部署上线用 uvicorn 启动服务~5分钟选择"当前进程启动"而非子进程

**💡 真实的软件工程是这样的**：
- 大量时间花在**探索和试错**（步骤②花的时间最多）
- 真正写代码的时间只占一小部分
- **好的设计**（简单可靠）比**炫酷的技术**重要得多

5.2 为什么 GA 特别适合学编程


其他框架（几万行代码）
    ↓ 小白看到就放弃了

GenericAgent（~3000行核心代码）
    ↓ 一周能读完

Agent Loop（~100行核心循环）
    ↓ 一天能理解

一个具体的子项目（generic_scraper, ~250行）
    ↓ 2小时能读完 + 能改

GA 的三大教学优势：


1. 极简：核心只有 3000 行，是其他框架的 1/10

2. 完整：从需求到部署，全链条可见

3. 可改：改一行代码就能看到效果，正反馈快
