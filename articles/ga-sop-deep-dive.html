一、🧠 GA Agent 核心系列（约 25 个 SOP）

总体画像：GA 的核心不是"一个 Agent"，而是一套元认知操作系统——通过 SOP 将 LLM 的思考过程结构化，把"AI 随机推理"变成"可预期、可控制、可复现的执行流水线"。

1.1 自主行动框架 (autonomous_operation_sop)

是什么：让 Agent 在用户离线时自主规划→执行→报告的完整闭环。核心是"写 TODO → 选一条 → 执行 → 写报告 → 记历史 → 结束"的循环。

为什么：用户不可能 24h 盯着 Agent。需要 Agent 在没有人类监督时，能自己找活干、自己评估价值、自己记录成果。核心价值公式：「AI训练数据无法覆盖」×「对未来协作有持久收益」。

代码实现：

  • 入口：autonomous_operation_sop.md 定义了完整流程
  • 工具脚本：helper.py 提供了 4 个核心 API：
    • get_todo() — 从 TODO.txt 读取待办列表
    • get_history(n) — 从 history.txt 读最近 n 条历史
    • complete_task() — 自动编号报告(R{NN})、移入 autonomous_reports/、prepend 历史行
    • set_todo() — 返回 TODO.txt 路径
  • 路径自动计算：基于模块位置 __file__.resolve().parent 定位 temp/、memory/、autonomous_reports/
  • 报告编号：_next_report_number() 通过正则 R(\d+) 扫描历史文件取最大号+1
  • 历史回滚：写入 history.txt 失败时自动回滚（移回报告文件）
# 典型自主行动流程
┌─────────────────────────────────────────────────┐
│ ① update_working_checkpoint 设置上下文           │
│ ② helper.get_history(40) + get_todo() 了解现状   │
│ ③ 选一条 TODO（不连续两次选相同子任务）            │
│ ④ 执行（≤30回合，小步快跑）                      │
│ ⑤ 收尾：重读SOP → 写报告 → complete_task()      │
│    → set_todo() 标记[x] → 结束                    │
└─────────────────────────────────────────────────┘

借鉴点：

  • "第一条选 TODO，做完就停" — 避免 Agent 陷入无止境执行
  • 三权分离：规划（task_planning.md）≠ 执行（TODO 循环）≠ 验证（subagent 评审）
  • 报告+历史双轨：报告给人读，历史给 Agent 读，各司其职

如果我们来写：我会用 Python pathlib 做路径管理，re 做报告编号提取，写 4 个纯函数。核心设计是幂等性——complete_task 可以重复调用不炸，历史写入有回滚。

1.2 开放目标模式 (goal_mode_sop)

是什么：让 Agent 长时间后台运行的模式——用户说"花 3 小时持续优化 X"，Agent 在后台一直跑，直到时间预算耗尽。

为什么：有的事情不是一次能做完的（比如持续优化、巡检、学习）。需要一个长期在后台跑、知道自己还有多少预算、时间到了自动收尾的 Agent。

代码实现：

  • 状态文件：temp/goal_state.json，含 objective、budget_seconds、start_time、turns_used、status
  • 启动：start /b python agentmain.py --reflect reflect/goal_mode.py（后台进程）
  • 多实例：通过环境变量 GOAL_STATE 指定不同的状态文件
  • 预算耗尽时自动进入"收口轮"然后停止
# goal_state.json 结构
{
  "objective": "用户原话目标",
  "budget_seconds": 10800,
  "start_time": 1745726400.0,
  "turns_used": 0,
  "max_turns": 200,
  "status": "running",
  "done_prompt": ""
}

借鉴点：

  • 状态外化— 所有运行状态写入 JSON 文件，而非留在内存。主进程挂了也能恢复
  • 预算控制— budget_seconds + max_turns 双重限制，防止无限循环
  • 多实例— 环境变量注入配置，一个代码跑多个 Agent

如果我们来写：关键在于状态文件的设计——把 "running/paused/stopped" 状态机和预算消耗逻辑分离。用 atexit 注册收尾函数，确保异常退出也能保存断点。

1.3 多步骤计划模式 (plan_sop)

是什么：3 步以上复杂任务的结构化执行框架。三个阶段：探索态(了解环境) → 执行态(按 plan.md 分步执行) → 验证态(subagent 独立验证)。

为什么：Agent 容易"一根筋"——拿到任务直接干，不先探测环境、不做计划、做完不验证。plan_sop 强制 Agent 先探索、再计划、再执行、再验证，是一个认知强制流程。

代码实现（262 行 SOP，含完整协议）：

  • 探索态：必须是 subagent 探测（主 agent 禁直接执行），结果写 plan_XXX/exploration_findings.md
  • 计划编写：主 agent 根据 findings 写 plan.md，步骤格式 [ ] / [D] / [VERIFY]
  • 执行态：循环读 plan.md → 找第一个 [ ] → 执行 → file_patch 标记 [✓] → 继续
  • 验证态：启动独立 subagent，给 verify_context.json（含任务描述/交付物清单/必做检查），做对抗性验证
  • 终止检查：file_read 全文扫描确认 0 个 [ ] 残留
  • 动态委托：执行中遇到 >3 文件/需调试/需浏览网页时，自动委托 subagent
# plan.md 格式
## 步骤
- [ ] P0: 探测环境 (subagent)
  task: xxx
- [✓] 安装依赖
  task: pip install xxx
- [VERIFY] 验证结果
  task: 启动验证subagent

借鉴点：

  • 纯文本协议— plan.md 就是 Markdown checklist，人类和 Agent 都能读
  • 三态分离— 探索/执行/验证 三个心智模式绝不混在一起
  • 强制验证— "主 agent 有确认偏误，易被表面成功迷惑"，所以必须独立 subagent 验证
  • 动态委托— 执行中遇到复杂度超限，不硬扛，立即委托 subagent

如果我们来写：不需要框架代码。核心就是一个 plan.md 文件 + 一个读取-执行-标记循环。我会用正则 \[ \] 检测待办，file_patch 标记完成，re.search 做终止检查。最难的部分是"探索态必须用 subagent"的自律约束——需要 Constitution 级别的硬编码。

1.4 监察者模式 (supervisor_sop)

是什么：一个只读、只判断、只干预的角色。它看着工作 Agent 干活，有问题才说话。

为什么：Agent 干活时会"沉浸"——忘记约束、跳步、光说不做。需要一个外部的"监工"角色，保持对 SOP 和约束的清醒认知。

实现方式：这不是代码实现，而是一个角色 SOP。关键机制：

  • 启动时读 SOP，提取约束清单（⚠️/禁止/必须/格式要求）
  • 监控循环：轮询 output.txt → 判断步骤 → 对照清单 → 需要时 _intervene 或 _keyinfo
  • 干预文件：_intervene（纠偏指令）、_keyinfo（预注入细节）
  • "沉默为主"——没问题不说话，说话一句话

借鉴点：

  • 监控而非执行— 清晰的角色边界，"你是挑刺的监工，不是干活的工人"
  • 干预粒度— 跳步/遗漏/光说不做/断言无据 等都有对应措辞
  • 预注入— 在工作 Agent 到达某步之前提前塞细节，而不是等犯错再纠正

如果我们来写：这不是代码问题，而是提示词工程。核心是写一个"监工角色定义"+ 一张干预条件表。关键设计决策：干预的触发条件要具体（不是"感觉不对"而是"跳步/遗漏/断言无据"）。

1.5 验证协议 (verify_sop)

是什么：对抗性验证协议——"能跑的必须跑，能看的必须看"。不是读代码验证，而是执行验证。

为什么：代码审查和测试都是 LLM 写的，可能全是 mock 和 happy path。需要独立第三方做工具驱动的验证。

协议设计：

  • 两个失败模式：验证回避（读代码就说 PASS）+ 被前 80% 迷惑（忽视最后 20% 空壳）
  • 铁律：必须运行、必须有工具输出、独立验证
  • 验证动作表：网页→截图+console 错误，脚本→执行+边界输入，数据→格式+行数+抽查
  • 对抗性探测：边界值(0/空/超长)、幂等性、缺失依赖、孤儿 ID
  • 输出格式：表格 | # | 验证动作 | 工具 | 关键输出摘要 | PASS/FAIL | + 裁定 VERDICT: PASS/FAIL/PARTIAL
  • 自检清单：BEFORE PASS / BEFORE FAIL 各有两个检查项

借鉴点：

  • "识别你的合理化借口"— 列出 LLM 最常见的逃避理由，提前打预防针
  • 产物类型→验证动作映射— 不用每次都推理"怎么验证"，直接查表
  • 对抗性探测必做— "至少运行一个，否则你只确认了 happy path"

如果我们来写：同样不是代码问题，而是一个验证规则引擎的提示词。重点是验证动作表和自检清单的设计。代码层面，可以写一个 verify_runner.py 自动读取产物类型，匹配验证动作并执行。

1.6 Code Review 模式 (review_sop)

是什么：对话内对抗性 Code Review。用户输入 /review 触发，主 Agent 在当前对话拉起评审，直接 echo 报告，不开 subagent、不落盘。

为什么：写完代码需要快速 Review，但不想切出当前上下文。review_sop 让 Agent 在当前对话内完成完整评审。

实现：

  • 入口：frontends/review_cmd.py:install() — monkey-patch GenericAgent._handle_slash_cmd
  • 底层：review_inline_prompt.txt + code_review_principles.md（15 条好代码原则）
  • 5 步工作流：读底料 → 锁定范围 → 逐文件读 → 回答 Q1-Q4 → 列 P0~P3 findings
  • 15 条代码原则：模块边界清晰、局部可推理、可组合、变化半径小、复杂度线性增长…
  • 8 条防误报规则：每条 finding 必须通过 Discrete & actionable / Introduced by this change / Not intentional… 等检查
  • 输出协议：Scope → Verdict → Summary → Design Challenge → Findings(P0→P3) → Cross-file notes → Regression tests

借鉴点：

  • 对抗性 framing— Q1-Q4 迫使 Reviewer 先质疑方案本身，再找 bug
  • 防误报八规则— 解决了 LLM Review 最头疼的"过度报告"问题
  • 15 条好代码原则— 不是最佳实践清单，而是评估维度，每条 finding 必须映射到其中一条
  • "Why-first" 措辞规范— 第一句给原因，不写"Great work, but..."

1.7 四层记忆治理 (memory_management_sop)

是什么：GA 最底层的记忆架构宪法。定义了 L1(极简索引) → L2(事实库) → L3(SOP/脚本) → L4(历史会话) 的四层记忆体系。

为什么：LLM 的上下文窗口有限，记忆如果膨胀就会挤占推理空间。需要一套信息分层+压缩+淘汰机制。

核心机制：

  • 4 条核心公理：
    1. 行动验证原则（No Execution, No Memory）— 只能存工具调用验证过的信息
    2. 神圣不可删改性— 验证过的有效配置/避坑指南在重构时严禁丢弃
    3. 禁止存储易变状态— 不存时间戳/PID/临时路径
    4. 最小充分指针— 上层只留能定位下层的最短标识
  • 决策树：环境特异性事实→L2，通用操作规律→L1 RULES，特定任务技术→L3，通用常识→丢弃
  • L1 同步规则：新增场景→低频→L3 列表加文件名；删除场景→删对应行；不搬细节
# 四层记忆示意
L1: global_mem_insight.txt (≤30行, <1k tokens)
    ↓ 导航指针
L2: global_mem.txt (环境事实, 分段组织)
    ↓ 详细引用
L3: memory/*.md, *.py (SOP/工具脚本)
    ↓ 定位过往
L4: L4_raw_sessions/ (历史会话, scheduler自动收集)

借鉴点：

  • "No Execution, No Memory"— 这个原则是防止 LLM 幻觉写入记忆的关键
  • L1 必须是存在性指针— "用什么 SOP 能做到什么"，而不是 How-to 细节
  • 命名自解释优先— SOP 名能说清楚的，L1 不加注释；改名的 ROI 高于改 L1

如果我们来写：重点在记忆的分层架构和同步规则。L1 用 patch 级别修改（不能 overwrite），L2/L3 可以增删。核心是写好"什么放哪层"的决策树。

1.8 进程记忆扫描 (procmem_scanner)

是什么：一个Windows 进程内存扫描器，支持 Hex 特征码搜索和字符串匹配，可选 LLM 增强模式输出上下文。

为什么：有时需要读取其他进程的内存数据（如微信自绘 UI 中的文本），用 Win32 API 直接 ReadProcessMemory。

代码实现（120 行 Python + ctypes）：

  • 定义 MEMORY_BASIC_INFORMATION 结构体 + OpenProcess/VirtualQueryEx/ReadProcessMemory 签名
  • scan_memory(pid, pattern, mode, llm_mode) 主函数：
    1. OpenProcess 获取句柄
    2. VirtualQueryEx 遍历内存页，跳过 State != MEM_COMMIT 或 Protect 不可读的页
    3. ReadProcessMemory 读取页数据
    4. 用 YARA（vs 2022 的 yara-python）做模式匹配（Hex 或字符串）
    5. LLM 模式：返回 base64+context，方便模型分析
  • CE 式差集扫描：一次全量 scan + 多次 ReadProcessMemory 筛选变化区域
# 核心扫描代码（简化）
def scan_memory(pid, pattern, mode='auto', llm_mode=False):
    h_proc = k32.OpenProcess(PROCESS_ALL_ACCESS, False, pid)
    curr_addr = 0
    while True:
        mbi = MEMORY_BASIC_INFORMATION()
        k32.VirtualQueryEx(h_proc, curr_addr, byref(mbi), sizeof(mbi))
        if mbi.State != MEM_COMMIT or ...: continue
        data = ctypes.create_string_buffer(mbi.RegionSize)
        k32.ReadProcessMemory(h_proc, mbi.BaseAddress, data, mbi.RegionSize, byref(read))
        # YARA 规则匹配
        if matches: 记录结果
        curr_addr = mbi.BaseAddress + mbi.RegionSize

借鉴点：

  • YARA 做模式匹配— 比暴力搜索快一个数量级，支持通配符 ??
  • LLM 模式— 返回带上下文的 base64 而非原始字节，让模型能直接理解
  • 差集扫描— 一次全量扫描 + 多次差分，定位动态变化的内存

如果我们来写：我会用同样的 ctypes + YARA 方案。关键优化点是跳过不可读页（节省大量时间）和模式长度检测（Hex 模式需要偶数字节长度）。

1.9 执行反思 (reflection_sop)

是什么：阻断"连续失败不断重试"恶性循环的自纠偏机制。3 次失败或 15 轮后触发，5 个问题自问。

为什么：Agent 会陷入失败循环——同一个操作反复试。需要一个机制在问题恶化前喊停，换方案或求助。

协议：

  • 触发条件：连续 3 次无实质进展 OR 已执行 ≥ 15 轮
  • 5 个问题：原始目标还记得吗？最近 3 步有实质进展吗？在重复失败操作吗？换方案是什么？需要请求用户吗？
  • 3 种结论：继续 / 微调(换工具/参数/顺序) / 暂停请求干预
  • 输出格式：📌 反思 @第N轮 + 状态 + 原因

借鉴点：

  • 前置 Constitution— 先自纠偏，再走 Rule 3 请求干预
  • 15 秒自问— 不耗时，但能有效阻断 Agent 的"僵尸执行"
  • 输出格式极简— 一行结论，不写长篇

1.10 定时任务 (scheduled_task_sop)

是什么：定时执行任务的系统。JSON 定义任务 → scheduler 60s 轮询 → 条件满足时触发。

为什么：有些任务需要定时执行（日报、巡检、监控），不能依赖用户手动触发。

实现：

  • sche_tasks/*.json 定义任务：{schedule, repeat, enabled, prompt}
  • repeat 支持：daily/weekday/weekly/monthly/once/every_Nh/every_Nd
  • scheduler.py 每 60s 轮询，条件：enabled=true + 时间≥schedule + 冷却已过
  • scheduler.health_check() 返回所有任务状态：HEALTHY/OVERDUE/DISABLED/NEVER_RUN/ERROR
  • once 类型执行一次后冷却 100 年（永不过期）

借鉴点：

  • JSON 任务定义— 比 crontab 更直观，可动态增删
  • 健康检查— 一目了然知道所有任务状态
  • 冷却时间防重复— 基于 done/ 目录的最新报告时间戳

1.11 Subagent 调用 (subagent.md)

是什么：GA 的子进程调用协议— 主 Agent 可以拉起一个独立的子 Agent 进程，通过文件系统通信。

为什么：主 Agent 的上下文是最稀缺资源。复杂探测、批量任务、独立验证应该交给子进程，主 Agent 只做决策和汇总。

实现：

  • 目录：temp/{task_name}/，包含 output.txt / reply.txt / _stop / _keyinfo / _intervene 等通信文件
  • 启动：python agentmain.py --task {name} [--input "txt"] [--llm_no N]
  • 通信协议：output.txt(append) → reply.txt(写回复) → output1/2/3.txt 循环
  • 两种模式：测试模式（行为验证）+ Map 模式（并行分发）
  • 子 Agent 内部可自行使用 plan_mode

借鉴点：

  • 文件系统通信— 简单可靠，比 RPC/消息队列轻量
  • Map 模式— 同构任务并行分发，独立上下文不污染
  • 监察模式— --verbose 输出原始工具结果，主 Agent 即使审查

二、🌐 浏览器/自动化系列（约 10 个 SOP）

总体画像：GA 的浏览器自动化不是 Selenium/Playwright。它通过 Chrome 扩展桥 (tmwd_cdp_bridge) + 物理键鼠 (ljqCtrl) + 视觉理解 (Vision API) 三层，覆盖了普通 Web 操作、硬编码触发的、验证码等所有场景。

2.1 TMWebDriver — 浏览器接管引擎

是什么：一个通过 Chrome 扩展接管用户真实浏览器（保留登录态/Cookie）的底层驱动。不是 Selenium/Playwright 的替代品，而是用户浏览器操作层。

为什么：很多操作需要用户的登录态（微信、淘宝、企业系统），用 Selenium 重登不现实。TMWebDriver 直接操作已登录的浏览器。

核心技术栈（137 行 SOP 记录了全部坑）：

核心能力矩阵

  • CDP 桥是首选— 绕过 isTrusted 检查，能同时实现 JS 灵活性和物理可靠性
  • 排查流程明确— 连不上时分 4 步排查：浏览器→WS后台→扩展→请求协助

2.2 ljqCtrl — 物理键鼠工具

是什么：基于 win32 API 的物理键鼠模拟工具。纯粹的底层操作——移动鼠标、点击、按键。

为什么：有些操作 JS 做不了（isTrusted=false），需要真实的人类操作。ljqCtrl 就是在操作系统层面模拟鼠标键盘。

代码实现（115 行 Python + win32api）：

  • DPI 感知：GetDeviceCaps(DESKTOPHORZRES) 拿物理分辨率，GetSystemMetrics(SM_CXSCREEN) 拿逻辑分辨率，算 dpi_scale
  • SetCursorPos(z)：输入逻辑坐标，内部乘以 dpi_scale 转物理
  • Click(x, y)：支持 tuple/双参数，内部转物理坐标后调用 mouse_event
  • Press(cmd, staytime)：解析 ctrl+v 为 VK_CONTROL + VK_V 组合键，查 VK_CODE 字典
  • FindBlock(fn, wrect, threshold)：OpenCV matchTemplate 匹配截图，返回物理坐标
  • GrabWindow(hwnd)：获取窗口截图（DPI 安全的坐标转换）
# ljqCtrl 核心 — DPI 感知 + 物理坐标
dpi_scale = cwidth / swidth  # 逻辑/物理 比值

def Click(x, y=None):
    if type(x) is tuple: x, y = x
    # 物理坐标 = 逻辑坐标 * dpi_scale
    SetCursorPos((int(x*dpi_scale), int(y*dpi_scale)))
    MouseDown(); time.sleep(0.05); MouseUp()

def Press(cmd, staytime=0):
    keys = cmd.lower().split('+')
    mods = [VK_CODE[k] for k in keys[:-1] if k in VK_CODE]
    main = VK_CODE[keys[-1]]
    for m in mods: win32api.keybd_event(m, 0, 0, 0)
    win32api.keybd_event(main, 0, 0, 0)
    time.sleep(staytime)
    win32api.keybd_event(main, 0, win32con.KEYEVENTF_KEYUP, 0)
    for m in reversed(mods): win32api.keybd_event(m, 0, win32con.KEYEVENTF_KEYUP, 0)

借鉴点：

  • DPI 感知是灵魂— 高 DPI 屏幕（4K/Retina）下逻辑/物理坐标换算不对，一切操作都偏移
  • 禁 pyautogui— 硬性约束（会污染 win32api）
  • FindBlock 截图匹配— OpenCV matchTemplate 做图色识别，给无 class/id 的按钮提供了点击方案
  • 窗口坐标转换陷阱记录— GetWindowRect vs ClientToScreen 的区别、DPI 是否 set aware 的区别，都写在 SOP 里

如果我们来写：核心是 win32api + ctypes（GetDeviceCaps 拿物理分辨率）。难点在坐标系统一——全程物理坐标，只在接口处做一次转换。VK_CODE 字典（映射 ctrl+v → 虚拟键码）是体力活。

2.3 Vision API — 视觉理解

是什么：多后端视觉理解 API，支持 Claude/OpenAI/ModelScope 三后端，截图后让大模型"看"。

为什么：有的页面状态用 DOM 读不到（canvas 渲染、自绘 UI、复杂图表），需要模型"看截图"来理解。

代码实现（114 行 Python）：

  • ask_vision(image, prompt, backend, timeout, max_pixels) 主入口
  • _prepare_image()：路径/PIL → JPEG base64，限制 max_pixels（默认 1440000）
  • 三后端走通：Claude（/v1/messages 含 image 块）、OpenAI 兼容（data:image/jpeg;base64）、ModelScope（同 OpenAI 兼容）
  • 配置从 mykey.py 读取（只读变量名，不读值）
# 三后端统一入口
def ask_vision(image_input, prompt="详细描述", backend='modelscope'):
    b64 = _prepare_image(image_input, max_pixels)
    if backend == 'claude': return _call_claude(b64, prompt, timeout)
    elif backend == 'openai': return _call_openai_compat(...)
    elif backend == 'modelscope': return _call_openai_compat(
        apibase='https://api-inference.modelscope.cn',
        apikey='ms-xxx', model='Qwen/Qwen3-VL-235B-A22B-Instruct'
    )

借鉴点：

  • 禁全屏截图— 能截窗口就不全屏，能截标题栏就不截窗口
  • 视觉 vs OCR 分工— Vision 只做"语义理解"，OCR 做"像素点击"，职责分离
  • 三后端+配置化— 不绑定单一模型，可从 mykey.py 动态读取

2.4 Vue3 组件破解 (vue3_component_sop)

是什么：绕过 Vue3 自定义组件 isTrusted=false 限制的终极方案——直接操作 Vue 组件实例。

为什么：Vue3 自定义组件（如 OxdSelect）监听的是真实硬件事件，JS dispatchEvent 产生的 isTrusted=false 事件被组件忽略。

实现（200 行 SOP + JS 代码）：

  • 法一：vnode 遍历 → findCompByEl(rootVnode, targetEl) 递归遍历虚拟 DOM 树找到组件实例，直接调 comp.proxy 方法
  • 法二：nativeSetter + 事件 → Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value') 拿原生 setter，然后 dispatch input/change 事件
  • 法三：具名插槽（Select 专用） → 找到 el-select 实例，ctx.states.selectedLabel = 'xxx'; ctx.onOptionClick(optionNode)
  • 法四：编辑器实例 API → Quill: el.__quill.setContent() / Tiptap: editor.commands.setContent()
  • 兜底：CDP Input.insertText— 绕过所有 isTrusted 检查
// Vue3 组件实例访问 — 终极破解
const rootVnode = document.getElementById('app')._vnode;
function findCompByEl(vnode, targetEl, depth = 0) {
    if (depth > 50 || !vnode) return null;
    const comp = vnode.component;
    if (comp) {
        if (comp.vnode?.el === targetEl || comp.subTree?.el === targetEl) return comp;
        if (comp.vnode?.el?.contains?.(targetEl)) {
            const result = findCompByEl(comp.subTree, targetEl, depth + 1);
            if (result) return result;
            return comp;
        }
    }
    // 递归 children + dynamicChildren
}

借鉴点：

  • 多层降级方案— 从最优(组件实例API)到次优(nativeSetter)到兜底(CDP 物理输入)
  • 编辑器识别表— class 名→编辑器类型映射，不用猜
  • "验证标准是提交对了不是看到了"— 拦截 fetch/XHR 看 payload，而非看页面显示

如果我们来写：核心是 vnode.component.proxy 的递归遍历。难点在动态 children 和 Teleport（Element Plus Select 选项被 Teleport 到 body）。我会先查编辑器私有字段（el.__quill），不行再走 vnode 遍历。

2.5 CDP 桥 — Chrome DevTools Protocol

是什么：tmwd_cdp_bridge 扩展，提供 WebSocket 直连 Chrome DevTools Protocol 的通道。

为什么：JS 有 isTrusted 限制、DOM 操作有边界。CDP 是浏览器内部协议，没有这些限制。

能力：

  • Page.captureScreenshot — 全页截图，前后台均可
  • Input.insertText / Input.dispatchKeyEvent — 绕过 isTrusted
  • DOM.getDocument({depth:-1, pierce:true}) — 穿透 Shadow DOM（含 closed）
  • DOM.getBoxModel — 获取元素坐标（四点平均，不是对角线平均——元素有 transform:rotate 时四点非矩形）
  • Page.bringToFront — 激活后台标签
  • DOM.setFileInputFiles — 文件上传（但 tmwd 桥中 nodeId 跨调用失效，不推荐）

借鉴点：

  • CDP 是"万能钥匙"— JS 做不到的（截图、物理输入、文件上传），CDP 都能做到
  • 但 CDP 也有坑— nodeId 在 DOM 变更后失效、跨域 iframe 需导航到目标域、后台标签节流
  • 分步 Shadow DOM— querySelector 不能跨 Shadow 边界，需先找 host 再在其 shadow 内找子元素

四、🔮 认知设计理念总结

读完全部 SOP 源码，最震撼的不是某个具体技术，而是背后的认知设计哲学：

1. 强制结构化推理

GA 不相信 LLM 的"自由推理"。每个 SOP 都把思考过程拆成固定步骤：

  • plan_sop 拆成 探索→计划→执行→验证 四步
  • autonomous_operation 拆成 读TODO→执行→写报告→记历史→结束
  • review_sop 拆成 读底料→锁定范围→读文件→Q1-Q4→列Findings

2. 上下文保护是第一优先级

主 Agent 的上下文是最稀缺资源：

  • 探索/验证必须用 subagent，主 Agent 不直接参与
  • plan_sop 中探索态强约束"禁止主 Agent 直接探测"
  • 信息分层 L1-L4，上层只存指针不存细节
  • L1 硬约束 ≤30 行

3. 对抗性思考嵌入

每个关键环节都嵌入"挑刺"视角：

  • verify_sop：你的两个失败模式 — "验证回避"和"被前80%迷惑"
  • review_sop：Q1-Q4 对抗性 framing，8 条防误报规则
  • supervisor_sop：干预条件表（跳步/遗漏/光说不做/断言无据）
  • memory_management：No Execution, No Memory — 防止幻觉写入

4. 可操作性 > 完备性

  • SOP 不追求覆盖所有场景，而是对高频场景给出精确的可操作指令
  • "验证标准是提交对了不是看到了" — 一句话比十页文档有用
  • "识别你的合理化借口" — 提前打预防针比事后纠偏有效

5. 犯错边界管理

  • reflection_sop：3 次失败或 15 轮后自纠偏
  • Constitution Rule 3：3 次失败请求干预
  • checkpoint 保存所有维度（页码/已采数/连续失败次数），支持精确恢复
  • "失败报告同样有价值" — 不要求每次都成功

五、📝 总纲：如果要写，怎么写？

基于对全部 SOP 源码的分析，总结我们写类似系统的方法论：

1. SOP 的写作范式

# 标题 — 一句话说清干什么用

> 一行的核心原则 / 警示

## 是什么（场景 + 价值）

## 为什么（不这么做的后果）

## 怎么做（编号步骤，每个步骤一个明确动作）

## 代码实现（关键代码片段，不需要完整文件）

## 铁律 / 红线（⚠️ 禁止 / 必须 / 格式要求）

## 避坑记录（具体环境下的失败模式）

## 验证标准（怎么确认做对了）

2. 代码工具的开发模式

1. **识别高频痛点** — 什么操作每次都要重写？→ 封装成工具函数
2. **纯函数优先** — 输入明确，输出明确，无副作用
3. **路径动态计算** — 基于 __file__.resolve().parent，不硬编码
4. **回滚/幂等** — 失败能回滚，重复调用不炸
5. **三后端/多配置** — 不绑定单一服务（Vision API 三后端）
6. **SOP + 代码分离** — SOP 写"怎么用"，代码写"怎么实现"

3. 如果让我们从头写一套类似系统

第一步：写 Constitution（宪法） — 定义 Agent 的行为边界（禁止什么、必须什么、失败怎么办）
第二步：写 Memory Management（记忆治理） — 定义信息分层 L1-L4 和存储规则
第三步：写 Plan SOP（规划模式） — 复杂任务的结构化执行框架
第四步：写核心工具 — Subagent（进程管理）、Verify（验证协议）、Reflection（反思纠偏）
第五步：写领域 SOP — 浏览器自动化、数据采集、电商等业务 SOP
第六步：建 SOP 市场 — sophub 式的社区生态

4. 最重要的几个设计决策

决策GA 的选择为什么
通信方式文件系统（非 RPC）简单可靠，可审计，不依赖网络
状态存储JSON 文件（非数据库）人类可读，工具无关，git 可追踪
记忆格式Markdown（非结构化数据）LLM 原生理解，人类也能读能改
浏览器接管Chrome 扩展桥（非 Selenium）保留登录态，绕过反爬
验证模式独立 subagent（非自验证）避免主 Agent 的确认偏误
任务规划plan.md checklist（非图形化）人和机器都能读，git 可 diff

5. 可以复用的套路

  • "先读再动" — 任何操作前先 file_read 了解现状
  • "小步快跑" — 每次只做一个子任务，做完就 checkpoint
  • "三层兜底" — 最优方案→次优方案→兜底方案（Vue3 操作的四层降级）
  • "纯文本协议" — Agent 之间通过 Markdown/JSON 文件通信，不发明新协议
  • "价值公式" — 用公式而不是感觉做决策：「AI训练数据无法覆盖」×「对未来协作有持久收益」
  • "对抗性思维" — 每个环节都假设自己会犯错，嵌入自检机制
