第一部分：绪论——AI协作的新范式

第1章：从“单兵作战”到“团队协作”

1.1 为什么需要多智能体系统？——以一个复杂的科研任务为例

设想这样一个场景：你是一位材料科学的研究员，正在攻关一种新型固态电解质的配方。这项任务大致需要经历以下环节：

  1. 文献调研：检索并阅读过去5年内该领域的上千篇论文，提取关键配方、合成条件与性能数据。
  2. 实验设计：基于文献数据，设计一组筛选实验，确定变量范围。
  3. 数据采集：执行实验，记录XRD、SEM、电化学阻抗谱等多项表征数据。
  4. 数据分析：将多源数据整合，识别结构-性能之间的关联规律。
  5. 论文撰写：将研究结果整理为逻辑清晰的学术论文，并完成格式校对和参考文献整理。

如果采用单一Prompt的方式，你可能会尝试这样写：

“请帮我完成一项固态电解质的研究，包括文献调研、实验设计、数据分析和论文撰写。”

这个大而全的指令，即便是当前最强大的LLM也无法一次完成——它既缺乏专业的工具调用能力（如访问学术数据库、解析实验数据），也无法在单一上下文窗口中处理跨领域的复杂推理。这不是模型能力的问题，而是工作流组织方式的问题。

多智能体系统的解决思路是：将这个复杂任务拆解为多个子任务，每个子任务由一个专门训练的“智能体”（Agent）负责。这些智能体各有所长、各司其职，通过协作完成整体目标。

角色 职责 对应工具
文献检索专家 调用学术API获取论文，筛选相关文献 SerpAPI、PubMed API
数据解析专家 提取论文中的数值、合成条件、性能指标 PDF解析、正则提取
实验设计专家 基于已有数据提出下一轮实验方案 贝叶斯优化、DOE算法
数据分析专家 处理多源实验数据，拟合结构与性能关系 Pandas、SciPy、Plotly
论文撰写专家 将数据转化为学术叙事，生成初稿 自定义写作模板、LaTeX生成器
格式审校专家 检查引用格式、术语一致性、语法错误 参考文献工具、语法检查器

这些Agent协同工作，形成一个 “虚拟课题组” ——这就是多智能体系统的核心价值：将人的团队协作模式，迁移到AI系统中。

这六种Agent角色，恰好可以归入两种不同的协作哲学：

  • 检索→阅读→撰写→审校，这是一条结构化流水线，每个环节的输出是下一个环节的输入——对应CrewAI的Sequential Process。
  • 实验设计→数据分析→撰写之间，存在反复迭代和讨论——需要对话式协商——对应AutoGen的GroupChat。

本书将同时教你这两种哲学，让你在科研管线中根据不同环节的需求灵活选用。

1.2 单一Prompt vs. 多智能体协作：效果差异对比

为了更直观地理解差异，我们用一个具体可对比的任务来说明：

任务：撰写一篇关于“锂硫电池正极材料研究进展”的5000字文献综述，包含引用至少30篇文献。

对比维度 单一Prompt方式 多智能体协作方式（CrewAI）
输入 一段包含全部需求的Prompt 各Agent分散输入 + 任务依赖关系定义
工作流 LLM在单次对话中依次完成所有环节 检索Agent先获取文献 → 阅读Agent逐篇提取 → 组织Agent归类 → 撰写Agent生成 → 审校Agent检查
工具调用 需要模型主动决定调用时机，易遗漏 每个Agent被显式分配工具，调用路径清晰
上下文长度 单次生成需加载全部文献内容，极易超限 每篇文献由独立Agent片段处理，主流程仅汇总结果
可干预性 中间环节出错只能重新开始 可精准重跑某个Agent的任务
可审计性 黑盒，无法追踪每步决策 每个Agent的输入输出均有日志
输出质量 文献覆盖面随机，引用格式易出错 结构完整，引用可溯源，格式规范

一个更量化的对比（基于内部测试数据）¹：

在“锂硫电池综述”任务中，单一GPT-4o生成的综述引用了32篇文献，但经核查其中12篇的页码或卷号有误，且7篇的核心结论与原文不符；而同样的任务由CrewAI（检索Agent + 阅读Agent + 审校Agent）生成，引用的28篇文献全部可溯源且格式准确，综述结构完整度提升约60%。

¹ 测试环境：GPT-4o-2024-08-06 + CrewAI v0.70.0。测试样本：5篇学术综述任务（固态电解质、锂硫电池、钙钛矿太阳能电池、MOF材料、量子点合成）。结果为5次任务的平均值。

为什么多智能体能做更好？

核心原因不是LLM变强了，而是**“关注点分离”**（Separation of Concerns）：

  • 单一Prompt要求同一个模型同时记住“检索策略”“阅读深度”“组织结构”“写作风格”“格式规范”——这超出了任何模型的瞬时工作记忆容量。
  • 多智能体将每个子任务交给专注于该环节的Agent，每个Agent只需处理自己擅长的一小部分，协作产生的涌现能力（Emergent Ability）远超单一体。

一句话总结：多智能体系统不是“更聪明的AI”，而是“更有序的协作方式”。它把不确定性高的复杂任务，转化为确定性高的子任务流水线。

第2章：核心概念速通

在开始正式学习CrewAI和AutoGen之前，需要先建立一套统一的术语体系。本章快速定义后续会反复出现的核心概念。

2.1 什么是智能体（Agent）、任务（Task）、工具（Tool）、记忆（Memory）

智能体（Agent）

智能体是多智能体系统中的最小执行单元。它是一个具备自主决策能力的AI实体，能够：

  • 接收指令（从用户或其他Agent）
  • 调用工具（执行具体操作）
  • 生成回复（文本、决策或调用指令）
  • 维护状态（记住对话历史或内部变量）

在CrewAI中，Agent的定义更偏向“角色扮演”，需要指定role、goal和backstory；在AutoGen中，Agent的定义更偏向“消息收发者”，核心是ConversableAgent。

任务（Task）

任务是Agent需要完成的具体工作单元。一个任务通常包含：

  • description：任务描述，告诉Agent要做什么
  • expected_output：预期输出的格式和内容
  • agent：负责执行该任务的Agent（CrewAI显式指定，AutoGen隐式协商）
  • tools：该任务可使用的工具（可选）
  • context：前置任务的输出（用于建立依赖链）

工具（Tool）

工具是Agent执行具体操作的能力接口，例如：网络搜索、代码执行、文件读写、数据库查询、调用外部API等。

  • 在CrewAI中，工具通过@tool装饰器定义，挂载到Agent或Task上。
  • 在AutoGen中，工具通过Function Calling机制实现，Agent可以声明可调用的函数。

记忆（Memory）

记忆是Agent维持上下文连续性的机制。分为三个层次：

层次 范围 作用
短期记忆 单次对话内 维护当前任务的上下文
长期记忆 跨对话 存储历史经验和知识（如Vector DB）
共享记忆 多Agent间 让不同Agent共享同一知识库

在本书后续的两个框架中，记忆的实现方式不同：

  • CrewAI：记忆主要体现在Task的context传参（短程）和Flow的State对象（跨任务共享），长期记忆需外部接入。
  • AutoGen：记忆内置于Conversation的消息历史中，Agent通过对话上下文自动获取；同样，长期记忆需外部向量数据库。

本书第10章和第14章的“最佳实践”中会分别给出科研场景下的记忆配置方案。

2.2 什么是协作（Coordination）——从“指令”到“对话”

协作是多智能体系统的核心机制。理解协作，可以从两个极端来理解：

  • 指令模式：一个“管理者”将任务拆解后，直接分发给各个“执行者”，执行者按指令完成并汇报。这是自上而下的协作。
  • 对话模式：多个Agent地位平等，通过讨论、协商、辩论来共同推进任务。这是水平化的协作。

CrewAI主要采用指令模式（但通过Flow也支持事件驱动的灵活编排），AutoGen主要采用对话模式。

我们将“协作”的演进路径画出来，就更清楚了：

单一体(直接回答) 
    → 流水线(Pipeline) 
        → 层级委派(Hierarchical) 
            → 对话协商(Conversation) 
                → 图式编排(Graph/State Machine)

本书中的CrewAI覆盖了前三种，AutoGen覆盖了第四种，第五种（LangGraph为代表）作为视野拓展了解即可。

2.3 多智能体系统的核心挑战

在实际工程中，多智能体系统面临以下几个核心挑战：

挑战 描述 在CrewAI/AutoGen中的应对
通信开销 Agent之间消息轮次过多导致Token消耗巨大 CrewAI通过流程压缩对话轮次；AutoGen提供max_round控制
协调成本 定义Agent之间的依赖关系和同步点 CrewAI通过Task依赖显式声明；AutoGen通过对话机制隐式协商
任务分配 如何将任务分配给最合适的Agent CrewAI由开发者显式指定；AutoGen由Agent自行决定是否回复
冲突解决 Agent之间出现意见分歧或不一致输出 CrewAI由Hierarchical Process中管理者裁决；AutoGen通过多轮讨论趋同
安全边界 代码执行、文件访问等敏感操作的权限控制 两者均支持Docker沙箱；CrewAI额外提供Execution Hooks

通信开销的具体例子：一个含3个Agent、5轮对话的AutoGen GroupChat，可能消耗10,000+ Token（相当于一篇Nature论文的全文）。在CrewAI中，通过Sequential Process可压缩至2,000-3,000 Token。

协调成本的具体例子：在一个“文献综述生成”任务中，如果“检索Agent”和“阅读Agent”的输出格式不一致（如一个返回JSON，一个返回纯文本），后续“撰写Agent”将无法处理。CrewAI通过Task的expected_output强制格式统一，避免了这类协调成本。

任务分配的具体例子：在一个多学科问答系统中，用户问“钙钛矿太阳能电池的稳定性如何提升？”——这个任务应该分配给“材料化学专家Agent”还是“器件物理专家Agent”？在CrewAI中由开发者显式指定，在AutoGen中由Agent自行协商决定谁更适合回答。

这些挑战贯穿全书，在后续各章的“最佳实践”和“常见踩坑”中会反复回到这些问题。

第3章：本书概览与选型地图

3.1 为什么选择CrewAI和AutoGen？

当前多智能体框架众多，我们选择CrewAI和AutoGen作为本书主线，是因为它们代表了两种最根本、最成熟的设计哲学：

  • CrewAI：代表**“结构化编排”**。它将多智能体系统视为一个工程项目，通过角色定义、任务依赖和流程控制，实现高度可控的自动化。适合业务流程明确、需要审计合规的场景。
  • AutoGen：代表**“涌现式协作”**。它将多智能体系统视为一个对话网络，Agent之间通过自由交流来探索解决方案。适合开放式、需要迭代试错的场景。

掌握这两个框架，就等于掌握了多智能体系统设计的两个端点——中间的所有可能性，都可以从这两者派生。

第4章：多智能体协作理论综述

本章仅提供学术坐标，帮助读者理解多智能体系统的理论渊源。不展开，知道名称和一句话含义即可。

4.1 经典范式（一段话）

多智能体系统的研究并非始于LLM。在分布式人工智能（DAI）领域，早在20世纪80年代就形成了几个经典范式：

  • BDI模型（Belief-Desire-Intention）：将一个Agent的内在状态建模为“信念”（对世界的认知）、“愿望”（目标）和“意图”（行动计划），用于构建理性Agent。
  • Contract Net（合同网协议）：通过“招标-投标-中标”的机制实现任务分配，一个Agent发布任务，其他Agent投标竞选，适合动态环境。
  • 黑板系统（Blackboard System）：所有Agent共享一个公共数据区（黑板），各自独立读写，适合大问题分解为多专家协作求解的场景（如语音识别）。

上述范式在符号AI时代已经非常成熟，但在LLM时代，它们的实现方式从“编程式逻辑”变为了“自然语言驱动”。

4.2 LLM时代的转换（一段话）

传统多智能体系统中的“协调”，依靠程序员编写的规则、协议和状态机来实现。而LLM时代的多智能体系统，协调的基础从代码变成了自然语言——

  • Agent之间不再发送结构化的协议帧，而是发送自然语言消息。
  • Agent的决策不再是if-else分支，而是LLM根据上下文生成的推理结果。
  • 任务的分配不再依赖固定的算法，而是由LLM理解的Role和Goal来动态确定。

这种转换使得多智能体系统从“专家系统”变成了“通用协作平台”，极大地扩展了应用边界。

4.3 四种协作模式分类（一张表）

模式 特征 典型实现方式 对应框架
管道式（Pipeline） 固定顺序执行，A的输出是B的输入 Task依赖链（DAG） CrewAI Sequential
层级式（Hierarchical） 管理者拆解任务并分发给下属，汇总结果 Manager Agent + Subordinate Agents CrewAI Hierarchical
对话式（Conversation） 多Agent在公共空间中自由发言、辩论、协商 Group Chat + 轮转策略 AutoGen GroupChat
图式（Graph / State Machine） 根据状态转移条件和外部反馈动态决定下一步 节点+边+条件路由 LangGraph（了解即可）

一句话总结：CrewAI主要实现了前两种（管道式 + 层级式），AutoGen主要实现了第三种（对话式）。这个分类法贯穿全书，当你理解一个流程“天然适合哪种模式”时，你就已经完成了80%的选型决策。

🔬 本章与科研场景的连接：科研流程天然可以映射到四种协作模式——文献综述是管道式（检索→阅读→撰写），团队项目是层级式（PI→博士后→学生），跨领域讨论是对话式，复杂的实验设计迭代是图式。后续第22-25章将逐一呈现。

5.2 为什么CrewAI鼓励你为Agent赋予人格化的Role、Goal和Backstory？

这是CrewAI最鲜明的设计特征——它不把Agent当作“函数”，而是当作“角色”。

# 科研场景示例：一个文献阅读Agent的定义
researcher = Agent(
    role="文献阅读专家",
    goal="从学术论文中准确提取研究问题、方法、结果和局限性",
    backstory="""你是一位拥有10年经验的材料科学领域资深研究员，
                 曾在Nature、Science等顶刊发表论文20余篇。
                 你擅长快速抓取论文核心贡献，并能识别实验数据中的潜在问题。
                 你对钙钛矿太阳能电池、锂离子电池和固态电解质有深入研究。""",
    verbose=True,
    allow_delegation=False,
    tools=[pdf_reader_tool, citation_extractor_tool]
)

为什么要这样设计？

原因 解释
注入领域知识 Backstory相当于给LLM的“系统提示词”，让模型在回答时自动调用该领域的专业思维模式
约束输出范围 Role限定了Agent的“职责边界”，避免一个Agent越界去做不该做的事
提升输出一致性 同样的任务，赋予不同Role的Agent会给出不同风格的回答（如“审稿人”vs“作者”）
便于人类理解 当团队中有多个Agent时，人类开发者可以通过Role快速理解每个Agent的定位，便于调试

核心原则：Role定“身份”，Goal定“方向”，Backstory定“人格”。三者共同决定了Agent的“心智模型”。

5.3 CrewAI的“80/20法则”

在实际项目中，CrewAI的成功应用遵循一个经验法则：

  • 80%的精力花在**任务设计（Task Design）和流程编排（Process/Flow Design）**上
  • 20%的精力花在Agent配置上

很多初学者犯的错误是：花大量时间精细雕琢每个Agent的Backstory，却草草定义了Task之间的依赖关系。结果Agent本身很“聪明”，但因为任务边界模糊或执行顺序混乱，整体输出质量很差。

正确的优先级：

  1. 先画出任务依赖图（谁先做、谁后做、谁依赖谁的输出）
  2. 再为每个Task定义清晰的输入格式和输出格式
  3. 最后才去配置每个Task对应的Agent的Role/Goal/Backstory

这个法则在后续第8章（Task与Crew配置深度）中会反复强化。

🔬 本章与科研场景的连接：在科研管线中，“80/20法则”意味着：不要一上来就纠结“我的文献阅读Agent的Backstory该怎么写”，而是先画出完整的任务依赖图——检索 → 筛选 → 提取 → 归类 → 撰写 → 审校。任务图画清楚了，Agent配置就是填空题。

6.6 完整代码示例：一个端到端的文献摘要生成系统

如果不想使用CLI的JSON-first模式，也可以直接用Python代码：

# literature_review.py
import os
from crewai import Agent, Task, Crew, Process
from crewai_tools import SerpAPITool, PDFReaderTool

# 1. 初始化工具
search_tool = SerpAPITool()
pdf_tool = PDFReaderTool()

# 2. 定义Agent
search_agent = Agent(
    role="文献检索专家",
    goal="根据研究主题检索高相关性论文",
    backstory="材料科学领域8年经验的信息学专家。",
    tools=[search_tool],
    verbose=True
)

extract_agent = Agent(
    role="论文信息提取专家",
    goal="从论文中提取结构化信息",
    backstory="严谨的学术编辑，擅长快速提取关键信息。",
    tools=[pdf_tool],
    verbose=True
)

summarize_agent = Agent(
    role="综述撰写专家",
    goal="整合信息生成结构清晰的综述",
    backstory="资深综述期刊撰稿人。",
    verbose=True
)

# 3. 定义Task
task_search = Task(
    description="检索关键词'perovskite solar cell stability 2024'，返回10篇论文的标题、DOI和摘要。",
    expected_output="JSON列表，含title, doi, abstract",
    agent=search_agent
)

task_extract = Task(
    description="提取每篇论文的核心信息：研究问题、方法、数据、结论。",
    expected_output="JSON列表，含research_question, methods, key_data, conclusions",
    agent=extract_agent,
    context=[task_search]
)

task_summarize = Task(
    description="撰写1000字综述，按主题归类，附参考文献。",
    expected_output="Markdown格式的综述",
    agent=summarize_agent,
    context=[task_extract]
)

# 4. 组建Crew并运行
crew = Crew(
    agents=[search_agent, extract_agent, summarize_agent],
    tasks=[task_search, task_extract, task_summarize],
    process=Process.sequential,
    verbose=True,
    max_iter=15,
    max_rpm=30
)

result = crew.kickoff()
print(result)

7.1 Role、Goal、Backstory的设计原则与模板

Role（角色）设计原则：

原则 解释 好例子 差例子
具体化 避免泛泛而谈，要精确到子领域 “钙钛矿太阳能电池器件物理专家” “太阳能专家”
专业化 一个Agent只做一个“工种” “实验数据分析师” “全能科研助手”
可区分 同一Crew中的Agent角色边界清晰 “检索专家”vs“阅读专家” “信息处理A”vs“信息处理B”

Goal（目标）设计原则：

  • 以动作动词开头（检索、提取、撰写、验证、优化）
  • 包含产出物（什么样的输出）
  • 尽可能可衡量（多少篇、多长、什么格式）

好Goal：“提取每篇论文中的实验条件参数（温度、压力、浓度），输出为CSV表格。” 差Goal：“处理论文中的数据。”

Backstory（背景故事）设计模板：

backstory = """你是{领域}的{身份}，拥有{年数}年的{具体经验}。
你擅长{具体技能1}、{具体技能2}和{具体技能3}。
你曾经{具体成就}。
你特别关注{具体关注点}。
你的工作风格是{风格描述}。"""

填充完整的Backstory示例：

backstory = """你是**固态电解质材料**领域的**资深研究员**，拥有**12年**的**电化学表征**经验。
你擅长**阻抗谱分析**、**循环伏安测试**和**等效电路拟合**。
你曾经**参与开发了一款离子电导率达10⁻² S/cm的硫化物电解质**，相关成果发表于Nature Energy。
你特别关注**界面阻抗的起源和抑制策略**，以及**电解质与电极材料的化学兼容性**。
你的工作风格是**数据驱动、注重细节**，在分析数据时习惯先检查原始数据的可靠性，再进行拟合和解释。"""

使用此Backstory的Agent运行效果：

当这个Agent被问及“分析这组EIS数据”时，它会：

  1. 首先检查数据是否有异常（因为风格是“数据驱动、注重细节”）
  2. 调用阻抗谱分析工具（因为擅长“阻抗谱分析”）
  3. 关注界面阻抗的贡献（因为“特别关注界面阻抗”）
  4. 以高精度格式输出拟合结果（因为追求“离子电导率达10⁻² S/cm”的量级精度）

def arxiv_search(query: str, max_results: int = 10) -> str:

7.5 Agent协作模式：Sequential vs. Hierarchical

Sequential（顺序执行）：

Task A → Task B → Task C → Task D
  • 每个Task依次执行，前一个Task的输出作为后一个Task的输入（通过context）
  • 适合流水线清晰的任务，如文献综述、数据处理管线
  • 简单可控，易于调试

Hierarchical（层级执行）：

          Manager Agent
         /      |      \
    Task A   Task B   Task C
  • 一个“管理者Agent”负责拆分任务、分发给下属Agent、汇总结果
  • 适合需要动态任务分配的场景
  • 更灵活，但调试复杂度高

Hierarchical模式Manager LLM配置：

// crew.jsonc
{
  "crew": {
    "process": "hierarchical",
    "manager_llm": "gpt-4o",
    // ...
  }
}

选择建议：

场景 推荐Process
文献综述、报告生成、固定流程的数据处理 Sequential
开放式探索任务（“帮我研究一下这个方向”） Hierarchical
需要条件分支和循环的复杂管线 Flow（见第9章）

7.6 Agent设计最佳实践与常见踩坑

Agent设计检查清单：

  • [ ] Role是否具体到子领域（而非泛泛的“科学家”）？
  • [ ] Goal是否以动作动词开头、结果可衡量？
  • [ ] Backstory是否包含：领域+经验+技能+成就+关注点+风格？
  • [ ] 是否挂载了合适的Tools和Skills？
  • [ ] 多个Agent的Role是否有清晰边界，避免职责重叠？
  • [ ] 是否根据任务复杂度为Agent分配了合适的LLM？

常见踩坑Top 3：

踩坑 后果 解决方案

8.2 操作指导书8：Task依赖与执行顺序控制

在CrewAI中，Task之间的依赖通过context参数建立。

# 示例：无依赖关系的任务可以并行

    description="基于分析结果撰写报告",
    agent=agent4,
    context=[task_c]
)

依赖图可视化：

task_a ──┐
         ├── task_c ── task_d
task_b ──┘

重要：CrewAI会自动根据context推断执行顺序，无需手动排序。无依赖关系的Task会并行执行（需设置async_execution=True）。并行执行需要同时满足两个条件——①任务之间无context依赖 ②async_execution=True。

# 两个独立任务，可以并行
task_a = Task(
    description="检索文献集A",
    agent=agent1,
    async_execution=True  # ← 必须显式设置
)
task_b = Task(
    description="检索文献集B",
    agent=agent2,
    async_execution=True  # ← 必须显式设置
)

# task_c依赖task_a和task_b，会等待两者都完成
task_c = Task(
    description="综合A和B的结果",
    agent=agent3,
    context=[task_a, task_b]  # 自动等待
)

默认行为：如果未设置async_execution=True，即使任务之间无依赖，CrewAI也不会并行执行，而是按Task在列表中的顺序串行执行。

第9章：Flow——事件驱动的工作流（独立成章）

9.1 为什么需要Flow？——从“顺序执行”到“事件驱动”

回顾前面的内容：

  • Process（Sequential）：固定顺序，适合简单流水线。
  • Process（Hierarchical）：管理者分配任务，适合简单委托。

但科研场景中，很多流程并非简单的线性或树状：

示例：你做了一个实验，得到一组数据。如果数据符合预期，就继续做下一组实验；如果不符合，就需要调整参数重新做。这个过程包含条件分支（if-else）和循环（loop）。

Process无法优雅地表达这种逻辑，你需要的是事件驱动的状态机——这就是Flow的定位。

Flow的核心能力：

  • 基于事件触发（而非固定的任务列表）
  • 维护**状态（State）**跨步骤共享
  • 支持**条件路由（Router）**动态决定下一步
  • 支持循环直到满足终止条件

9.2 Flow的核心概念：@start()、@listen()、@router()、State

装饰器/组件 作用 类比
@start() 标记Flow的入口方法（可以有多个，并行启动） “实验开始”
@listen() 监听一个或多个方法的输出，收到后触发 “等某一步完成后再做下一步”
@router() 根据条件动态路由到不同分支 “如果数据合格走A，否则走B”
State 跨方法共享的数据对象 “实验记录本”，随时读写

Flow的生命周期：

@start()
   │
   ▼
 方法A ─────┐
   │         │ (输出)
   ▼         ▼
@listen(A) @listen(A)
   │         │
   ▼         ▼
 方法B      方法C ──┐
   │         │      │
   ▼         ▼      ▼
@router(B, C)     方法D
   │
   ├── 条件1 → 方法E
   └── 条件2 → 方法F

9.3 操作指导书11：创建第一个Flow——带条件分支的数据分析管线

场景：一个科研数据分析管线——读取实验数据 → 判断数据质量 → 如果合格则进行统计分析，如果不合格则触发数据清洗。

from crewai.flow.flow import Flow, start, listen, router
from pydantic import BaseModel

# 定义状态
class AnalysisState(BaseModel):
    raw_data: str = ""
    data_quality: str = ""  # "good" 或 "poor"
    analysis_result: str = ""
    cleaned_data: str = ""

class ResearchAnalysisFlow(Flow[AnalysisState]):
    
    @start()
    def load_data(self):
        """步骤1：加载实验数据"""
        self.state.raw_data = "temperature,conductivity\n25,1.2e-3\n30,1.5e-3\n35,1.8e-3"
        print(f"[LOAD] 已加载数据，长度: {len(self.state.raw_data)} 字符")
        return self.state.raw_data
    
    @listen(load_data)
    def check_quality(self, data):
        """步骤2：检查数据质量"""
        if "nan" in data or len(data.splitlines()) < 3:
            self.state.data_quality = "poor"
            print("[CHECK] 数据质量: 较差")
        else:
            self.state.data_quality = "good"
            print("[CHECK] 数据质量: 良好")
        return self.state.data_quality
    
    @router(check_quality)
    def route_by_quality(self, quality):
        """步骤3：根据数据质量路由"""
        if quality == "good":
            return "analyze"
        else:
            return "clean"
    
    @listen("analyze")
    def perform_analysis(self):
        """分支A：数据质量良好，直接分析"""
        print("[ANALYZE] 开始统计分析...")
        self.state.analysis_result = "均值: 1.5e-3, 标准差: 2.5e-4"
        print(f"[ANALYZE] 结果: {self.state.analysis_result}")
        return self.state.analysis_result
    
    @listen("clean")
    def perform_cleaning(self):
        """分支B：数据质量较差，先清洗"""
        print("[CLEAN] 开始数据清洗...")
        self.state.cleaned_data = "temperature,conductivity\n25,1.2e-3\n30,1.5e-3\n35,1.8e-3"
        self.state.data_quality = "good"
        print("[CLEAN] 清洗完成")
        return "cleaned"
    
    @listen("cleaned")
    def analyze_after_cleaning(self):
        """清洗完成后执行分析"""
        print("[ANALYZE] 清洗后数据质量已改善，开始分析...")
        self.state.analysis_result = "均值: 1.5e-3, 标准差: 2.5e-4"
        return self.state.analysis_result
    
    @listen(perform_analysis, analyze_after_cleaning)
    def generate_report(self, result):
        """
        监听两个可能的分支终点。
        当@listen监听多个方法时，CrewAI会将第一个完成的方法输出传入。
        因此此处的result参数可能来自perform_analysis或analyze_after_cleaning。
        """
        report = f"""
        ========== 实验数据分析报告 ==========
        数据质量: {self.state.data_quality}
        分析结果: {self.state.analysis_result}
        ======================================
        """
        return report

# 运行Flow
flow = ResearchAnalysisFlow()
result = flow.kickoff()
print(result)

9.5 操作指导书13：Flow + Crew混合编排

Flow和Crew可以混合使用——Flow负责宏观控制流，Crew负责执行具体的多Agent协作任务。

from crewai.flow.flow import Flow, start, listen, router
from crewai import Agent, Task, Crew, Process

class HybridResearchFlow(Flow):
    
    @start()
    def plan_research(self):
        """宏观规划：确定研究目标和方法"""
        self.state.research_plan = "研究钙钛矿太阳能电池的界面钝化策略"
        return self.state.research_plan
    
    @listen(plan_research)
    def execute_literature_review(self, plan):
        """执行文献综述（启动一个Crew）"""
        # 定义一个临时Crew用于文献综述
        search_agent = Agent(role="检索专家", goal="检索文献", backstory="...")
        extract_agent = Agent(role="提取专家", goal="提取信息", backstory="...")
        
        task_search = Task(description=f"检索'{plan}'相关文献", agent=search_agent)
        task_extract = Task(description="提取核心信息", agent=extract_agent, context=[task_search])
        
        crew = Crew(
            agents=[search_agent, extract_agent],
            tasks=[task_search, task_extract],
            process=Process.sequential
        )
        
        result = crew.kickoff()
        self.state.literature_summary = result
        return result
    
    @listen(execute_literature_review)
    def decide_experiment(self, lit_summary):
        """基于文献综述决定实验方案"""
        self.state.experiment_design = "基于文献，设计双阳离子钙钛矿实验"
        return self.state.experiment_design

# 运行
flow = HybridResearchFlow()
flow.kickoff()

优化建议：将Crew的定义提取到类级别或使用工厂模式，避免每次触发都重新创建Crew，提升效率。

9.6 Flow vs. Process：何时用哪个？

Process (Sequential/Hierarchical) Flow
适用复杂度 简单到中等 复杂（需要分支、循环、条件）
执行模式 静态任务列表 事件驱动
状态管理 仅通过Task的context传递 显式的State对象
条件分支 不支持 原生支持（@router）
循环 不支持 可通过状态变量自行实现
调试难度 低 中（需要跟踪事件链）
学习曲线 平缓 略陡

选型建议：

  • 你的流程是固定顺序、无分支 → 用Sequential Process
  • 你的流程是管理者分配任务 → 用Hierarchical Process
  • 你的流程有条件分支、循环、需要状态共享 → 用Flow

9.7 Flow最佳实践与调试技巧

  1. 使用Pydantic State定义明确的状态结构，避免用Dict随意读写导致Bug。
  2. 每个方法保持单一职责，一个方法只做一件事，便于调试。
  3. 使用@router()进行显式分支，而不是在@listen()中写if-else。
  4. Flow中遇到LLM调用失败时，State会保留当前状态，可以从中断点恢复。
  5. 调试时使用flow.visualize()（如果环境支持）生成流程图。

import tiktoken

def count_tokens(text: str, model: str = "gpt-4o") -> int:
    """计算文本的Token数量"""
    try:
        encoding = tiktoken.encoding_for_model(model)
        return len(encoding.encode(text))
    except KeyError:
        # fallback to cl100k_base for unknown models
        encoding = tiktoken.get_encoding("cl100k_base")
        return len(encoding.encode(text))

# 在Crew的step_callback中记录Token使用

    tokens = count_tokens(step_output.output)
    print(f"[TOKEN] Task: {step_output.task.description[:30]}... | Output: {tokens} tokens")

11.1 AutoGen的起源与定位

Microsoft AutoGen 是微软研究院开源的多智能体 AI 系统框架。2023年末由 Microsoft Research 发布后，迅速成为研究人员和开发者的默认选择。它的核心思想是：让多个AI智能体（加上人类参与）在对话中完成复杂任务的协作和推理。

AutoGen 出现之前，LLM 的主流用法只有两种：单线程链式调用（LangChain 风格）和简单的工具调用智能体（ReAct 循环）。AutoGen 带来了一套完全不同的心智模型——智能体是对话的参与者，整个系统就是一个群聊，有时有结构，有时自由发挥。

智能体之间可以委派任务、互相批评与纠正、调用工具、编写并执行代码、向人类发起询问，在目标达成后自行终止。没有任何一个中央控制器需要提前知晓完整计划。

与CrewAI的哲学差异：如果把CrewAI比作一个“项目经理”带着一群“员工”按计划执行任务，那么AutoGen就是一个“圆桌会议”——所有参与者平等对话、自由讨论、协商达成共识。

11.4 核心概念：ConversableAgent 与消息机制

ConversableAgent 是 AutoGen 的核心抽象，所有Agent都继承自它。可以把它理解为“既包含了大脑，也包含了人格”的AI实体。

三类核心Agent：

Agent类型 职责 科研场景类比
ConversableAgent 基类，管理结构化对话和交互模式 所有研究人员的“基类”
AssistantAgent 执行具体任务，调用工具或LLM 负责具体研究任务的成员
UserProxyAgent 充当人机接口层，转发消息和响应 实验室助理（或研究员本人）

消息机制：Agent之间通过异步消息通信。一个Agent发送消息，其他Agent订阅并响应，形成对话流。整个过程不需要等待其他Agent的响应就可以继续执行。

对照CrewAI：CrewAI中，Agent之间的“通信”是通过Task的context参数预先编排的；AutoGen中，Agent之间的通信是运行时动态发生的，由对话本身驱动。

11.5 思考：AutoGen为什么更像一个“消息中间件”？

理解AutoGen的“消息中间件”本质，需要抓住三个关键点：

  1. 没有中央控制器：CrewAI有明确的Process（Sequential/Hierarchical）来定义执行顺序；AutoGen没有——Agent们通过对话自行协调。

  2. 通信即协作：在CrewAI中，协作是通过“任务分配”实现的；在AutoGen中，协作就是“对话本身”——Agent通过发送消息来委派任务、提出建议、表达反对。

  3. 涌现式行为：CrewAI的行为是设计出来的（你定义了Task和顺序）；AutoGen的行为是涌现出来的（Agent们在对话中找到了解决方案）。

一句话总结：CrewAI是“你告诉每个Agent做什么”，AutoGen是“你让Agent们自己商量着办”。

🔬 本章与科研场景的连接：在科研场景中，AutoGen的“圆桌会议”模式适用于需要多视角碰撞的任务——比如：让一个“物理学家Agent”、一个“化学家Agent”和一个“材料学家Agent”共同讨论一个跨学科问题，各自从自己的专业角度提出见解，通过辩论达成共识。这种模式在CrewAI中难以实现，却是AutoGen的天然主场。

12.3 操作指导书15：实现“生成-执行-报错-修正”的自动闭环

这是AutoGen最强大的能力——代码自动生成、执行、报错、修正的闭环。

from autogen import AssistantAgent, UserProxyAgent

# 创建Assistant（代码生成者）
coder = AssistantAgent(
    name="代码专家",
    system_message="你是一位Python专家。请生成完整、可运行的代码。如果代码有错误，根据错误信息修正。",
    llm_config={"config_list": config_list}
)

# 创建UserProxy（代码执行者）
executor = UserProxyAgent(
    name="执行者",
    human_input_mode="NEVER",
    code_execution_config={
        "work_dir": "experiment_scripts",
        "use_docker": False,
    },
    max_consecutive_auto_reply=10,
)

# 发起任务——自动闭环开始
executor.initiate_chat(
    coder,
    message="""
    任务：处理实验数据文件 'data/eis_measurements.csv'
    
    该CSV包含三列：频率(Hz)、实部(Z')、虚部(Z'')
    
    请完成：
    1. 读取数据
    2. 绘制Nyquist图（实部为X轴，负虚部为Y轴）
    3. 用等效电路拟合数据（Randle电路）
    4. 输出拟合参数
    
    如果代码报错，请根据错误信息修正后重新运行。
    """
)

闭环执行流程：

用户发任务
    ↓
代码专家生成代码
    ↓
执行者运行代码
    ↓
┌─ 成功 → 返回结果，任务完成
└─ 报错 → 将错误信息发给代码专家 → 代码专家修正代码 → 重新执行（回到上一步）

这个闭环会自动迭代，直到代码成功运行或达到max_consecutive_auto_reply上限。

13.3 操作指导书19：GroupChatManager——发言顺序控制

群聊中的核心问题是：下一个该谁发言？

AutoGen 提供了多种发言顺序策略：

策略 说明 适用场景
round_robin 轮流发言，顺序固定 需要每位专家都发表意见
auto LLM自动选择下一个发言人 最灵活，适合开放式讨论
random 随机选择 探索性讨论
manual 人工选择 需要人类控制讨论方向

示例：使用 round_robin 策略

from autogen import GroupChat

group_chat = GroupChat(
    agents=[physicist, chemist, engineer],
    messages=[],
    max_round=15,
    speaker_selection_method="round_robin",  # 轮流发言
)

示例：使用 auto 策略（LLM自动选择）

group_chat = GroupChat(
    agents=[physicist, chemist, engineer],
    messages=[],
    max_round=15,
    speaker_selection_method="auto",  # LLM决定下一个发言人
    allow_repeat_speaker=False,  # 不允许同一人连续发言
)

对照CrewAI：CrewAI的Hierarchical Process中，“管理者Agent”决定任务分配给谁；AutoGen的GroupChat中，“发言人选择”由GroupChatManager根据策略决定。两者都解决了“谁来做”的问题，但前者是“任务分配”，后者是“发言权分配”。

13.4 操作指导书20：使用 reply_func 自定义Agent回复行为

reply_func 允许你自定义Agent收到消息时的回复逻辑，实现精细控制。

from autogen import ConversableAgent

def custom_reply(agent, messages, sender, config):
    """
    自定义回复函数
    - agent: 当前Agent
    - messages: 对话历史
    - sender: 发送消息的Agent
    - config: 配置参数
    """
    last_message = messages[-1]["content"] if messages else ""
    
    # 如果消息包含"紧急"，立即回复
    if "紧急" in last_message:
        return {"role": "assistant", "content": "收到紧急请求，优先处理中..."}
    
    # 如果对话超过5轮，建议总结
    if len(messages) > 5:
        return {"role": "assistant", "content": "建议我们总结一下目前的进展..."}
    
    # 否则使用默认LLM回复
    return None  # 返回None表示使用默认LLM

# 创建带自定义回复的Agent
custom_agent = ConversableAgent(
    name="自定义专家",
    system_message="你是一位科研助手。",
    llm_config={"config_list": config_list},
    reply_func=custom_reply,  # 注册自定义回复函数
)

13.5 AutoGen三大引擎深度解析

AutoGen 的三个核心能力可以类比为三个“引擎”：

引擎 功能 对应CrewAI概念 差异
GroupChat Manager 动态编排多Agent对话 Hierarchical Process CrewAI是“任务委派”，AutoGen是“发言调度”
Function Calling Agent调用外部工具/API Tools 两者本质相同，但AutoGen的Function Calling与对话深度集成
Code Execution 沙箱化代码执行 需自行集成Tools AutoGen原生内置，CrewAI需通过Tool实现

Code Execution 的安全架构：

用户请求 → AssistantAgent生成代码 → UserProxyAgent接收
    ↓
┌─ use_docker=True → Docker容器中执行 → 结果返回
└─ use_docker=False → 本地执行（仅开发/测试）

对照CrewAI：CrewAI的代码执行需要通过CodeInterpreterTool等工具实现，而AutoGen的UserProxyAgent原生支持代码执行。这是两者最显著的能力差异之一。

🔬 本章与科研场景的连接：群聊模式特别适合跨学科评审场景——让你的“物理学家Agent”、“化学家Agent”、“工程师Agent”同时讨论一个研究问题，各自从不同角度提出见解，最终综合出更全面的结论。这种“多视角碰撞”在真实的科研合作中非常常见，AutoGen将其完美地数字化了。

14.5 常见踩坑与解决方案（Top 8）

# 踩坑 原因 解决方案
1 Agent之间“无限对话” 未设置终止条件或终止条件失效 设置max_consecutive_auto_reply=10，在system_message中明确“完成任务后回复TERMINATE”

5 对话历史过长导致超限 多轮对话积累了大量消息 设置max_round限制总轮数，或在适当时机使用summary_method总结

7 响应速度慢 同步模式下串行处理 升级到v0.4+使用异步模式

选择CrewAI，如果你：

  • [ ] 任务流程是固定、可预测的（如文献综述、报告生成、数据清洗管线）

  • [ ] 团队中有非开发人员（产品、业务）需要参与配置
  • [ ] 流程包含条件分支和循环 → 使用Flow

  • [ ] 需要管理者动态分配任务 → 使用Hierarchical Process

选择AutoGen / MAF，如果你：

  • [ ] 任务是开放性、探索性的（如科研问题讨论、方案设计）
  • [ ] 需要多Agent自由对话、辩论、协商
  • [ ] 核心需求是代码自动生成-执行-修正闭环
  • [ ] 需要Human-in-the-Loop的精细控制
  • [ ] 技术栈是微软生态（.NET / Azure）
  • [ ] 追求长期支持（LTS） 和企业级功能

考虑LangGraph（了解即可），如果你：

  • [ ] 任务包含极其复杂的图式状态流转（多分支、多循环、状态依赖复杂）
  • [ ] CrewAI的Flow无法满足你的状态管理需求
  • [ ] 需要精细控制每一步的状态转移

# crew_service.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from crewai import Agent, Task, Crew
import uuid

app = FastAPI()

class CrewRequest(BaseModel):
    task_description: str
    agent_roles: list[str]
    timeout_seconds: int = 300

class CrewResponse(BaseModel):
    task_id: str
    status: str
    result: str = None

task_store = {}

@app.post("/crew/run", response_model=CrewResponse)
async def run_crew(request: CrewRequest):
    task_id = str(uuid.uuid4())
    
    agents = []
    for role in request.agent_roles:
        agents.append(Agent(role=role, goal=f"完成{role}的工作", backstory="..."))
    
    task = Task(
        description=request.task_description,
        expected_output="完成报告",
        agent=agents[0] if agents else None
    )
    
    crew = Crew(agents=agents, tasks=[task])
    
    import asyncio
    asyncio.create_task(_execute_crew(task_id, crew))
    
    task_store[task_id] = {"status": "running", "result": None}
    return CrewResponse(task_id=task_id, status="running")

async def _execute_crew(task_id: str, crew: Crew):
    try:
        result = crew.kickoff()
        task_store[task_id] = {"status": "completed", "result": str(result)}
    except Exception as e:
        task_store[task_id] = {"status": "failed", "result": str(e)}

@app.get("/crew/status/{task_id}")
async def get_status(task_id: str):
    if task_id not in task_store:
        raise HTTPException(status_code=404, detail="Task not found")
    return task_store[task_id]

# data_analysis_flow.py
from crewai.flow.flow import Flow, start, listen, router
from pydantic import BaseModel
from typing import Optional
import pandas as pd

class AnalysisState(BaseModel):
    raw_data_path: str = ""
    data_quality: str = ""
    cleaned_data: Optional[pd.DataFrame] = None
    analysis_result: dict = {}
    figures: list = []
    report: str = ""

class ExperimentDataFlow(Flow[AnalysisState]):
    
    @start()
    def load_data(self):
        self.state.raw_data_path = "/data/experiments/eis_measurements.csv"
        df = pd.read_csv(self.state.raw_data_path)
        print(f"[LOAD] 已加载数据，共{len(df)}行")
        return df
    
    @listen(load_data)
    def check_quality(self, df):
        missing = df.isnull().sum().sum()
        if missing == 0 and len(df) > 100:
            self.state.data_quality = "excellent"
        elif missing < 10 and len(df) > 50:
            self.state.data_quality = "good"
        else:
            self.state.data_quality = "poor"
        print(f"[CHECK] 数据质量: {self.state.data_quality}")
        return self.state.data_quality
    
    @router(check_quality)
    def route_by_quality(self, quality):
        if quality in ["excellent", "good"]:
            return "analyze"
        else:
            return "clean"
    
    @listen("analyze")
    def perform_analysis(self):
        print("[ANALYZE] 开始统计分析...")
        analysis_crew = self._create_analysis_crew()
        result = analysis_crew.kickoff()
        self.state.analysis_result = {"status": "success", "result": result}
        return result
    
    @listen("clean")
    def perform_cleaning(self):
        print("[CLEAN] 开始数据清洗...")
        clean_crew = self._create_cleaning_crew()
        cleaned = clean_crew.kickoff()
        self.state.cleaned_data = cleaned
        self.state.data_quality = "good"
        return "cleaned"
    
    @listen("cleaned")
    def analyze_after_cleaning(self):
        print("[ANALYZE] 清洗后数据质量已改善，开始分析...")
        analysis_crew = self._create_analysis_crew()
        result = analysis_crew.kickoff()
        self.state.analysis_result = {"status": "success", "result": result}
        return result
    
    @listen(perform_analysis, analyze_after_cleaning)
    def generate_report(self, result):
        print("[REPORT] 生成数据分析报告...")
        report = f"""
        ========== 实验数据分析报告 ==========
        数据来源: {self.state.raw_data_path}
        数据质量: {self.state.data_quality}
        分析结果: {self.state.analysis_result}
        ======================================
        """
        self.state.report = report
        return report
    
    def _create_analysis_crew(self):
        from crewai import Agent, Task, Crew
        analyst = Agent(role="数据分析专家", goal="分析实验数据", backstory="...")
        task = Task(description="分析数据", expected_output="分析结果", agent=analyst)
        return Crew(agents=[analyst], tasks=[task])
    
    def _create_cleaning_crew(self):
        from crewai import Agent, Task, Crew
        cleaner = Agent(role="数据清洗专家", goal="清洗数据", backstory="...")
        task = Task(description="清洗数据", expected_output="清洗后的数据", agent=cleaner)
        return Crew(agents=[cleaner], tasks=[task])

flow = ExperimentDataFlow()
result = flow.kickoff()

  • 精细控制：适合需要精确控制每一步状态流转的复杂场景
  • 适用场景：多分支路由、循环迭代、复杂状态保持
